## 4. HOW IT LANDS — his unit, never his text rewritten (L28)

His answer unit `drc-trades/voice-<trade_id>` is created blank once and never upserted (V10). The transcript must reach it without ever changing a byte he wrote.

`[F-01 — OPEN — ROUND 2, R2-V1 on the initial-body clause only]` Grok T-V1, verbatim: "His unit `drc-trades/voice-<trade_id>` is created once by the DRC build's `upsert_unit(..., skip_if=…)`, and that call is never used on it again. `skip_if` is true whenever that unit id is already in the note, including when the body already holds transcript blocks. A new `VaultWriter.append_to_unit(unit_id, block)` is the only later Cobalt write into the unit: it calls `_session_gate`, reads the body under the existing mtime guard, and commits only when the new bytes are exactly the bytes just read, plus one separator, plus one block. It does not merge, reorder, delete, or apply the sync-revert win. It is idempotent on the capture row: if that row already has a landed write id, or that capture id is already in the body, it links the row and writes nothing. A re-transcribe is a new row and a new block, never a replacement of the old block. The build does not call `append_to_unit`. No sibling transcript unit is built."

- SETTLED by all three seats that ruled (idempotency; hub WRONG FACTS 3 HOLDS, FC1 HOLDS): the landing op is idempotent — a retry after a crash between the vault commit and the row update writes nothing twice. The proposal's bare byte-prefix check is replaced. The sibling-unit alternative is not built (3 of 3).
- OPEN to round 2 (R2-V1): whether the build seeds the unit's INITIAL body with already-bound transcript blocks and never calls the append (the proposal's §4.1, grok, gemini (f)), or creates the unit BLANK as v2 T6 does and lands every transcript — at build time too — through ONE landing function that calls the append (the Fable seat). Both positions, verbatim, in the derive report. X3 runs under either answer.
- He edits freely below or around the blocks; the transcript block is his text the moment it lands — Cobalt never touches that block again (no "correct the transcript" rewrite). A re-transcribe (§6) lands a NEW block labelled `re-transcribed capture <id>`, never replaces the old one.
