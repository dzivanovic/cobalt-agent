## §3 THE COMPLETE DESIGN AS IT NOW STANDS
### 3.1 Partitioning (T1 — closed 3-0 in round 2; restated unchanged)
`system.bars` becomes a native `PARTITION BY RANGE (ts)` parent with **weekly** children. Bounds are **generated in code**, never typed: for each Monday, `datetime(y, m, d, 0, 0, tzinfo=ZoneInfo("America/New_York"))`, emitted as `timestamptz` literals; `TO` of week n is `FROM` of week n+1. A test asserts: contiguity over 2026–2027; no bound inside 04:00–20:00 ET of any calendar day; the week of 2026-11-01 is 169 h and the week of 2027-03-14 is 167 h. The parent carries `PRIMARY KEY (ticker, interval, ts)` and **`CHECK (interval = 'i1')`**. No `DEFAULT` partition. Width is revisable FORWARD only (a later period may be daily without touching a stored row); the trigger to narrow is §3.8's row signal, never a ticker count. Partition width bounds rows per partition, **not** total proof work: every writable or invalidated partition is read. Until the swap the partitioned parent exists under a working name (`system.bars_p`) and is **empty**.

### 3.2 Partition creation, and the poller with no partition (T2)
- **Created by migration**, ≥26 weeks ahead (PROPOSED tunable). `cobalt bars partitions ensure --horizon N` is idempotent, runs through the migration harness's connection as a named deploy step or by an operator; never a resident, never cron. `placement.py` gains a pattern rule admitting partition children, `bars_digest` and `bars_legacy` on the system side (today it names `bars` only, `:35`), with a per-table PROOF POLICY (§3.3, §3.4 step 7).
- **Heartbeat probe:** contiguous coverage of `[now − (measured vendor window + 2 days), now + horizon]`, by bounds, not by child count. AMBER < 8 future weeks; RED < 2 or ANY hole (PROPOSED tunables). Retention and repairs may never leave a hole inside that reach-back without the probe going RED for the duration. The reach-back is the G0-measured vendor window (§6 U1), never the constant 15.
- **What happens today if a partition is missing** (`radar/poller.py:104-115`): the insert raises, the poller catches `BaseException`, the first statement after the `StageDropped` test is `scrub(str(e))` (`:112`), a generic per-ticker `error` is recorded and the loop continues — ≈500 identical failures whose cause is only in the log. No crash. At that line the poller holds `closed`, `now`, `watermark` and `e`; it holds no partition bounds; `now` is the wrong proxy (Monday 04:00:30 the 04:00 bar is not closed, `:99-101`, so `closed` still ends Friday 19:59).
- **THE RULE (astra, verbatim):** *"Identify missing-partition failures using structured store diagnostics and partition bounds, not the exception class or batch maximum alone. After rolling back a failed batch, determine all uncovered submitted timestamps and independently verify coverage of the current period. Missing current coverage aborts the cycle and marks radar health RED; historical-only holes remain per-ticker failures with explicit reconciliation ranges. If coverage cannot be established, abort with an explicit coverage-unknown failure. Test a batch containing both historical and current holes, regardless of which row fails first."*
- **How the rule is met without reading an exception:** once per poll CYCLE (not per ticker) the store reads the parent's partition bounds (`pg_inherits` + `pg_get_expr(relpartbound)`). (1) If the period containing `now` is not covered → the cycle aborts before the first fetch, radar health RED/degraded (L9: a card must not show Friday's last minute as live). (2) If the bounds cannot be read → abort, class `coverage_unknown`. (3) Per ticker, `closed` is divided by the bounds BEFORE the write: the covered rows go through today's single `executemany` unchanged; the uncovered rows are not submitted and become one per-ticker failure of class `no_partition` carrying the ticker and the uncovered range (the class and the range only, never row text) — so a new mover whose 14-day export overlaps one missing historical week still gets its current-week bars (grok's intent, without per-week transactions). (4) If the write raises anyway (a partition detached between the read and the write), the batch has rolled back atomically: the bounds are re-read once; missing current coverage → abort; otherwise that ticker fails with `no_partition` and the loop continues. Nothing in this path parses `e`.
- **Recovery:** `ensure`, then `cobalt archiver backfill-missing` for the named tickers/ranges inside the vendor window. The design reconciles explicitly and does not rely on the next poll self-healing (§6 U6).
- This is a change on the live radar's write path: smallest possible diff, ≥3 checkers (L67), its own tests (a batch with a historical hole only; a current hole only; both, in either row order; bounds unreadable; a detach between read and write). It lands with chunk 2 and is inert until the parent is partitioned (before the swap `bars` is a plain table: the bounds query returns "not partitioned" → today's behaviour, byte for byte).

### 3.3 The migration proof (T3)
**Why the brief's 15.7 s failed (4 of 4, round 1):** 507.3 rows/ticker/day is a blend (a liquid name carries 960); "only the open week is re-read" is false — `upsert` nights push the whole ≈14-day export through `upsert_bars` (`archiver/runner.py:237-253`), the poller's first sight of a ticker writes the whole export in session (`radar/poller.py:96-102`), `append` reaches today + 2 completed sessions that the export carries (`archiver/reconcile.py:71`); and the harness connects as the docker **superuser with no `SET ROLE`** (`db.py:269-285`), so a REVOKE proves nothing about the one actor the proof audits.
**THE RULE (astra, verbatim):** *"MP1 remains the default. MP2 may trust a sealed baseline only under a demonstrated invalidation and sealing protocol. Seal publication must serialize with writes, atomically recording a digest, exact count and generation without clearing a concurrent invalidation. Unexpected changes to SEALED content are incidents; do not silently replace the trusted baseline. Use ALWAYS DML triggers, explicit TRUNCATE handling, and validation of bounds, schema, membership and trigger definitions. Digest the union of partitions invalidated before or during the migration and compare against their trusted pre-migration content. Privileged operations capable of bypassing invalidation require an in-transaction content proof before commit; an evening bracket is additional detection, not deployment authorization. If bypass cannot be excluded, use MP1."*
**What that means in order:**
1. **MP1 is what every deploy runs** — PK-ordered whole-table md5 of `bars`, before and after, any `CHANGED` rolls back before commit (`db_migrations/cli.py:689-696`) — until (a) chunk E has DEMONSTRATED the protocol below and (b) he has ruled §4 item 5. MP1's cost after the swap: 62.1 s, growing 15.68 s for every further week of hot rows (§7). It stays byte-compatible as `--proof-only --full` forever.
2. **The candidate MP2 protocol, to be demonstrated, not assumed:**
   - Ledger `system.bars_digest(partition, lower, upper, state, digest, row_count, schema_hash, trigger_def_hash, generation, sealed_at, dirty, dirtied_at, relfilenode, n_tup_ins, n_tup_upd, n_tup_del)`; `row_count` is the fold's exact count, never `reltuples`/`relpages`.
   - States: **OPEN** (current week; no trigger on the 04:00 hot path; always digested in the outage) · **CLOSED-MUTABLE** (upper bound younger than the measured vendor window + 2 days: legitimately rewritten) · **SEALED** (older).
   - Invalidation: a row-level DML trigger on every non-OPEN child, created **`ENABLE ALWAYS`** (grok, gemini, astra), setting `dirty`; a statement-level `TRUNCATE` trigger on the same children; a dirty SEALED partition is an **incident** and its trusted baseline is never silently replaced.
   - In the outage, for every non-OPEN, non-dirty partition (grok's wording): it *"must equal its last-seal `(relfilenode, n_tup_ins, n_tup_upd, n_tup_del)`. Any move forces a content digest of that partition in the same run. … a stats reset breaks equality → re-digest, never 'counters went down so no writes'."* Plus validation of bounds, schema hash, `pg_inherits` membership + OIDs, and the trigger definition AND its function body (`trigger_def_hash`). Whether the migration's OWN uncommitted DML is visible to such a check (`pg_stat_xact_user_tables` vs the cumulative view) decides whether this is a pre-commit guard at all → **E-7**.
   - The harness digests OPEN + every dirty or moved partition and compares against the trusted pre-migration content; it prints per table one of **`CONTENT_VERIFIED` / `SEALED_BASELINE_TRUSTED` / `NOT_CONTENT_VERIFIED`** and never "content UNCHANGED" for content it did not read.
   - **Seal publication serialises with writes:** sealing (nightly after the archiver, and at deploy preflight — both inside the 20:00–21:00 market_reset pause or overnight idle, never in a scanning session) takes `LOCK TABLE <child> IN SHARE ROW EXCLUSIVE MODE` under `lock_timeout`, digests, and publishes digest + exact count + generation in the same transaction; a writer waits ≤ one child's one-sided digest (≈7.8 s at 1,332,705 rows). It never clears a `dirty` it did not read under that lock. The lock-free compare-and-clear alternative is only an E-10 comparison, not the design.
   - A repair of a SEALED week is a controlled **reopen → repair → re-digest → reseal**, generation + 1 (the seam option D needs, §4 item 4).
   - The off-outage post-deploy bracket (one pass over the SEALED region, residents up) STAYS as additional detection. **It is never deployment authorization** unless he explicitly accepts that exposure (§4 item 5).
3. **If chunk E cannot exclude a bypass** (any of E-3, E-6, E-7, E-8, E-9 fails its expectation): fallback **F-A, needing no decision:** MP1 stays; its growth is bounded only by how many weeks are hot (his retention rulings, §4 items 1–2). Fallback **F-B, only on his explicit word:** in-outage digests of OPEN + CLOSED-MUTABLE + dirty, SEALED partitions checked by `relfilenode` + membership + the full SEALED digest run OFF the outage immediately before the drain and immediately after the restart — honest label `NOT_CONTENT_VERIFIED in the outage`; the exposure is "a wrong SEALED price sits in the table from the commit until the post-deploy bracket ends". Whether any card-path reader can reach a SEALED week in that interval is §6 U18.
4. **A migration's text is a trigger for `--full`, never an authorization:** a migration whose SQL names `bars`, a partition, `bars_digest`, `session_replication_role`, `DISABLE TRIGGER`, `DETACH`/`ATTACH`, `TRUNCATE` or the trigger function forces MP1 for that deploy. A `DO` block with dynamic SQL evades a text scan — which is why this is a widening rule only.
