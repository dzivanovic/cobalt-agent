## 0. The restart question, answered first

**`com.cobalt.heartbeat` is a 15-minute one-shot, not a resident process.**

```
$ launchctl print gui/501/com.cobalt.heartbeat
	state = not running
	runs = 339
	program = /Users/cobalt/.local/bin/uv
	arguments = { uv run cobalt heartbeat beat }
	working directory = /Users/cobalt/cobalt
	StartInterval = 900
```

`state = not running` between beats, with a run counter — launchd spawns
`uv run cobalt heartbeat beat`, it exits, launchd waits 900 s. **New code
is therefore picked up at the next beat with no restart of anything**, and
none was performed.

### ESCALATE — production runs whatever is checked out here

The consequence nobody wrote down: that `working directory` is
`/Users/cobalt/cobalt`, **the same checkout this branch was built in**.
So `git checkout sprint-1/email` deployed the branch to production the
moment the next beat fired. Evidence — the 11:20 ET beat ran the new code
before consent existed, and its DM said so:

```
email channel DOWN: vault has no GOOGLE_OAUTH_REFRESH_TOKEN — consent has
never been granted on this host. Run `cobalt notify email-auth`.
DM sent — post 3e16u4otcin5uxuabcs6oj3t1y to @dejan_z
```

That is the F18 wiring working, and it is also an unplanned production
deploy of uncommitted-at-the-time work. NN#16 says dev is a *git worktree
checkout*; the prompt's `BRANCH: … from main` instruction, taken literally
in the primary working directory, bypasses that. **Every launchd job has
the same property** — they all point at this directory.

This is not a defect in what was built; it is a standing hazard in how the
jobs are wired, and it will bite again on any branch that is red at the
moment a beat fires. Two ways out, Dejan's call:

1. point the production plists at a dedicated checkout (a worktree pinned
   to a tag), so `main`/branches here stop being live; or
2. accept it explicitly and treat every branch in this directory as a
   production deploy, with the sprint discipline that implies.

### Design decisions worth knowing

- **No `token.json`.** The library's usual pattern writes a live refresh
  token to a plaintext file inside the git repo. Instead the OAuth triple
  lives in VaultManager and an access token is minted per send and thrown
  away — one extra HTTPS round trip, and one fewer file to gitignore, back
  up, rotate and remember.
- **Three separate vault keys**, not one JSON blob, so an F19 literal hit
  reports `literal:GOOGLE_OAUTH_REFRESH_TOKEN` — which names the credential
  to rotate. A blob would report the parent key and leave the operator
  guessing.
- **`static_discovery=True`.** `googleapiclient.discovery.build` otherwise
  fetches a discovery document over the network, growing the alert path a
  third endpoint that nothing monitors. With it, a send makes exactly two
  outbound calls.
- **`http=` rather than `credentials=`.** `build(credentials=…)` builds an
  `httplib2.Http` with **no timeout** — an alert about a dead service could
  hang forever on a half-open socket. `AuthorizedHttp` binds
  `notify.email.timeout_s` to the refresh *and* the send.
- **`out_of_band()` runs before `send_dm()`.** The DM body renders from
  `beat.notes`, so the email outcome must be in that list first. That
  ordering is what puts `email channel DOWN: <reason>` in the red DM. Only
  one direction works: the DM can report on the email channel; the email
  channel cannot report on itself.
- **A new table, not the heartbeat's job row.** `cobalt_jobs.last_result`
  is written only by the heartbeat, so `email-test` — the exact command
  used to *prove* the channel — would leave no trace the probe could read.

## 2. The dependency chain

A send **requires**, and requires nothing else:

1. `COBALT_MASTER_KEY` on the process;
2. `data/.cobalt_vault` readable + `GOOGLE_OAUTH_CLIENT_ID` /
   `_CLIENT_SECRET` / `_REFRESH_TOKEN`;
3. `configs/cobalt/notify.yaml`, `configs/cobalt/redact.yaml`,
   `configs/cobalt/taxonomy/tunables.yaml` readable;
4. HTTPS to `oauth2.googleapis.com` (refresh) and `gmail.googleapis.com`
   (send).

A send **does not require** — this is the property F18 buys:

- **Postgres.** Nothing on the path opens a connection. F19's redaction
  counter and `record_attempt()` both write rows, and both swallow their
  own failure by contract; the redaction itself is pure string work that
  has already happened.
- **Mattermost.** No import, no socket, no shared credential.
- **The Obsidian vault.** `cobalt.vault.resolve_vault_path()` is never
  called.
- **The mainframe, the ASET sheet**, or any other monitored service.

The only overlap with the monitored world is the **local disk** (vault file
+ config files). A host with no disk cannot alert by any means; claiming
otherwise would be theatre.

## 4. Two defects found and fixed in the consent flow

Both surfaced the first time `email-auth` ran non-interactively, and both
made the command look hung.

1. **Block-buffered stdout.** The command blocks on a socket for as long as
   a human takes to click through a consent screen, and the first thing it
   must emit is the URL that human needs. Python block-buffers stdout when
   it is not a tty, so the URL sat in an 8 KB buffer until the process
   exited — after it was needed. `run_consent_flow` now line-buffers stdout
   before anything prints.
2. **`socket.getfqdn("localhost")` takes 35 seconds on this host** —
   measured. `wsgiref` calls it during `server_bind`, and
   `run_local_server` binds *before* printing the URL, so the command was
   silent for 35 s. `_fast_local_bind()` patches `getfqdn` for the bind and
   restores it immediately (it is a shared builtin; a surviving override
   would surprise every later caller). `SERVER_NAME` is read by nothing on
   this path.

   **Forward DNS is 0.01 s here**, so the *send* path never went near this
   and `notify.email.timeout_s = 20` is not at risk.

## 5. Tunables added (F16)

| key | value | unit | consumers |
|---|---|---|---|
| `notify.email.auth_port` | 8765 | count | `run_consent_flow` (loopback bind); the OAuth client's registered redirect URI (human-entered) |
| `notify.email.timeout_s` | 20 | duration | `send_email` (token refresh + Gmail send) |

`auth_port` must be **fixed**, not ephemeral: Google requires every
redirect URI to be pre-registered, so the library's `port=0` default
produces `redirect_uri_mismatch`. The port has to be knowable by a human
editing the Google console *before* the client exists — which is exactly
what a config row is for. `unit: count` is the least-wrong `TunableUnit`
member; inventing a `PORT` unit for one row would change the taxonomy
schema for no analytical gain.

`timeout_s` is deliberately longer than `heartbeat.probe_timeout_s` (5 s):
a probe that hangs delays a beat, but this is the alert itself, and a red
that gave up after 5 s on a slow uplink is a red nobody receives. Still far
inside the 900 s interval, so a hung send cannot overlap the next beat.

**No threshold was put in `notify.yaml`** — the config block is exactly
`{enabled, to, subject_prefix}` as specified, and the loader forbids extra
keys.

## 6. F19

The three `google_oauth_*` shapes already existed in `redact.yaml`, written
speculatively before any send path did. They are now **live** and were
documented as such rather than duplicated (duplicate pattern names crash
the loader by design).

Both new values are additionally enrolled in the **literal** guard, by the
same mechanism that enrolled `MATTERMOST_DB_PASSWORD` on 09-05: every vault
entry over `literal_min_length` is loaded automatically. `put_secret`
clears the guard's cache on write, so enrolment is immediate rather than at
the next restart — the refresh token cannot leak through the channel that
minted it.

Proven by `test_the_new_shapes_are_redacted_out_of_an_outbound_email`
(pattern half, vault deliberately empty of the values),
`test_the_stored_credential_is_redacted_by_the_LITERAL_guard`, and
`test_the_SUBJECT_is_redacted_too` — the subject matters as much as the
body, being what appears in a phone notification and every mail-server log
on the way.
