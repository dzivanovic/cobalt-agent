## 4. Radar real cadence — facts only, nothing edited

### 4.1 Is 100 s the sleep or the period? **The sleep.**

| claim | evidence |
|---|---|
| `scan_interval` is the pause BETWEEN cycles | `radar/runner.py:345-348`: `while should_keep_running(...): result = await runner.cycle(); logger.info(...); await asyncio.sleep(interval)`. The sleep follows the cycle; it is not a period. |
| the log timestamp is cycle **END** | same three lines — the `logger.info` is after `await runner.cycle()` returns. So the gap between two log lines = `interval` + the duration of the second cycle. |
| the tunable | `configs/cobalt/taxonomy/tunables.yaml:428-429` `radar.scan_interval: 100`; `:455-456` `radar.finviz_max_rpm: 45`; `configs/cobalt/radar.yaml:21` `list_chunk_size: 50` |

The desk's 09-17 "≈189 s apart, not 100 s" observation is confirmed and explained. It is not drift and not a bug.

### 4.2 What bounds a cycle's duration? **The token bucket, and nothing else that is measurable.**

`TokenBucket` (`radar/collector.py:38-67`): `rate = rpm/60` tokens per second, **`capacity = 1.0`** — a burst of exactly one. `acquire()` holds a lock while it waits, so requests are serialised, and each request after the first starts `60/rpm` seconds after the previous one. Every Finviz request goes through it: pool bars (`radar/poller.py:87-88`, one `acquire` + one fetch per member, sequential) and every screen and list chunk (`collector.py:152-158`).

So the predicted cycle duration is `(N − 1) × 60 / rpm`, where N is the requests issued that cycle. Member count enters only through N. Per-request latency does not enter at all as long as it stays under `60/rpm` (1.33 s at rpm 45), because the bucket's wait absorbs it.

**Measured, and it matches to within a second — in two different rate regimes:**

| regime | ceiling | measured period | n | predicted cycle `(61−1)·60/rpm` | measured cycle (period − 100) |
|---|---|---|---|---|---|
| premarket 09-18 06:18:44 → 06:48:35 | 45 | **179.128 s** mean (min 179.080, max 179.236) | 10 gaps over 1791.276 s | 80.0 s | **79.13 s** |
| premarket 09-17 07:50–08:00 (desk) | 40 | ≈189 s | 3 starts | 90.0 s | ≈89 s |
| overnight idle 09-18 03:22:24 → 03:59:05 | — | **100.036 s** mean | 22 gaps over 2200.794 s | 0 (an idle cycle issues no request — `runner.py:166-167` returns before `_collect`) | **0.036 s** |

The idle measurement is the clean control: with no requests the gap is `scan_interval` to within 36 ms, which pins the loop shape exactly.

Both scanning regimes imply the same request count — `79.13 × 45/60 + 1 = 60.3` and `89 × 40/60 + 1 = 60.3` — against a planned 61. The small shortfall has a named cause: `planned_total_rpm` prices the pool at `pool.cap` (50), while the poller polls only the members in ADMIT/RETAIN/HOLD that cycle (`runner.py:230-233`), which is at or just below the cap when a ticker churns.

### 4.3 Measured requests/min vs `planned rpm 36.60`

`planned_total_rpm` (`radar/notes.py:219-240`) = `(pool.cap + screen_count + list_chunks) × 60 / scan_interval`. From the live `36.60` and `scan_interval 100`, N = 61 = **cap 50 + 4 screens + 7 list chunks** (`Radar Screens.md: 5 blocks ok` counts the pool block too — `sources.py:145` prints `len(parsed.screens.blocks)`, while `notes.py:177` counts `ScreenBlock` only).

| | value |
|---|---|
| planned | **36.60 rpm** |
| measured (N=61 over the measured 179.128 s period) | **20.43 rpm** |
| measured (N=60.3 implied) | **20.20 rpm** |
| ratio | the budget check overstates real demand by **≈1.79×** |

**Why, exactly:** the formula divides by `scan_interval`, but the real period is `scan_interval + cycle duration`. `planned_rpm` is therefore the **limit** of the true rate as the ceiling goes to infinity — a strict upper bound, never an estimate. It errs in the safe direction, and L53's total-demand rule still holds; it just has far more headroom than it shows.

A second guarantee, from the code rather than from measurement: the resident can never exceed the ceiling, whatever the interval. `real = 60N / (I + 60(N−1)/C) < C` reduces to `60 < C·I`, true for every ceiling and interval in play. The bucket alone enforces L53's ceiling; the planned-rpm check is a second, stricter gate on top of it.

### 4.4 Cap / interval pairs under ceiling 45 and 50

`P` = `pool.cap`; N = P + 11 (4 screens + 7 chunks, unchanged by P). Minimum interval the **formula** permits is `I ≥ 60N/C`. Real period is `I + 60(N−1)/C`; real rate is `60N/period`.
