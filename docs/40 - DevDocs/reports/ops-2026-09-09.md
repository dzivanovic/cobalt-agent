## C. `vault restore`, per write

**Commit** `ce32fae`.

### Defect 1 — section-wide
A unit write was rolled back by replacing the **whole section** from
`vault_writes.before`, so every sibling unit written after it went with
it. The daily note carries `rules` (05:15) and `heartbeat` (every 15 min)
in one section: undoing a heartbeat write took the morning's rules block.
**A rollback that cannot be used on any note with two units is not a
rollback.**

Now a row with a `unit` and a non-null `unit_before` puts back only that
unit's body, located by its own stable-id marker inside the section. If
the write **created** the unit — its open marker is absent from the
recorded before-section — the unit is *removed* rather than emptied;
leaving a marker pair around nothing would be a Cobalt artifact the
before-state never had.

### Defect 2 — no frontmatter undo
`upsert_region` writes into a span located by a **callable**, and a
callable cannot be persisted, so `restore` looked for a section marker,
found none (frontmatter cannot carry one) and refused. 102 of the sprint's
writes were frontmatter; a restic snapshot was their only rollback.

`_locate_region` finds it two ways, both evidence rather than inference:
structurally via `frontmatter_span` when that block still holds exactly
the bytes the row wrote, and otherwise **by content** — `unit_after` *is*
what the write left on disk, so a single contiguous match is the region.
That covers every other `locate` shape (the seat-usage human cells, and
anything added later) with no registry of locators to keep in step.

### Refusals stay loud
Zero matches → *"no longer on disk as it was written"*. More than one →
*"the anchor is ambiguous"*. Unit gone → *"not in section … refusing to
guess"*. All three tested.

### Legacy rows are unchanged
A row with no `unit`, or one written before `unit_before` existed, has
nothing to locate a unit by and gets the original whole-section replace.
Tested by nulling the column on a real row.

### Proof — 14 tests on the dev vault + `cobalt_dev`
The three the prompt names, verbatim in intent:

* two-unit section → write unit 1 → write unit 2 → restore unit 1's
  write → **unit 2 intact**, and the human line typed between them
  survives;
* frontmatter write → restore → **file byte-identical to before**
  (`note.read_bytes() == before`);
* legacy row → old behaviour.

`--dry-run` shows the diff and writes nothing; the sibling appears only
as *unchanged context*, never as a `+`/`-` line.

### Deviation
One test initially used a real trade name in a fixture and the L31/L32
lint (`test_names_rule.py`) caught it. Correct catch — changed to
`example-trade`. Recorded because it is the lint doing exactly its job.

## D. A sync revert is not a human override

**Commit** `b544c53`.

### What happened, and what it cost
On 2026-09-09 the daily note's `heartbeat` unit was stuck on the 05:54
GREEN block from 06:25 to 08:05. The 06:09 and 06:24 beats wrote RED; at
06:25:54 Obsidian Sync carried a stale copy up from another device and
put the 05:54 text back. Every beat after that saw on-disk != baseline,
concluded *"a human edited this"*, let the human win, and recorded
overrides 30–34. Cobalt could not write its own status block for an hour
and forty minutes, and the audit trail said a person had insisted on it
five times.

**A human edit is NEW text; a sync revert is OLD text coming back** — and
that evidence was already in `vault_writes` and simply never consulted.

### What changed
* `store.recent_afters(note, section, unit, limit=10)` → `(id,
  unit_after)`, newest first. Answers *"is the body on disk something
  Cobalt wrote HERE at all"*, which is not the question `last_after()`
  asks.
* `VaultWriter._merge_base` — **the ONE place either write path decides
  its merge base**, called by `upsert_unit` and `upsert_region` alike.
  On a match: base := the on-disk text, so Cobalt's new text wins
  cleanly; **no override rows**; a loud `logger.warning`; a
  `WriteResult.notes` line; and `sync_revert_of` on the row.
* Migration `0004_vault_writes_sync_revert.sql` (nullable `INTEGER`, no
  FK — the writer purges at 30 days and a FK would block or cascade)
  plus `0004_…rollback.sql`.
* `cobalt vault writes` prints it.

### Proof — today's shape replayed on the dev vault

```
write A id      : 12965
write C id      : 12967
C.sync_revert_of: 12965
overrides       : 0
on disk         : True

WARNING  cobalt.vaultwrite.writer:_merge_base:877 - vaultwrite: SYNC REVERT in
  …/2026-09-09.md [cobalt-status/heartbeat] — on-disk body matches vault_writes id 12965
  (2026-09-09 13:43:56.483669+00:00). Obsidian Sync is the usual cause. Taking the
  on-disk text as the merge base; NOT recording an override.

NOTE: SYNC REVERT: the text on disk is byte-identical to vault_writes id 12965
  (2026-09-09 13:43:56) — an earlier Cobalt write coming back, not a human edit.
  Cobalt's new text wins cleanly; no override recorded.
```

```
$ uv run cobalt vault writes --limit 3

        ^ SYNC REVERT of write 12965 — the text on disk was an earlier Cobalt write
          coming back (Obsidian Sync is the usual cause), not a human edit. No override recorded.
 12966  2026-09-09 13:43:56  proof.0909  cobalt-status  heartbeat  …/2026-09-09.md

```

Rows and scratch folder removed afterwards.

**The regression:** a *real* human edit still produces an override —
text Cobalt never wrote lands in `vault_overrides`, `sync_revert_of` is
NULL, and the human's words are on disk (L28.2 intact). Tested.

### The window is bounded, and the false positive is named
Ten writes. A body older than that is **not** silently assumed to be
Cobalt's own — it is treated as a human edit, which is the safe
direction, and there is a test for it. The false positive — a human
hand-typing, or MANUALLY RESTORING, a byte-identical copy of one of the
last ten blocks (Dejan putting back text Cobalt wrote earlier today) — is
classified sync-revert and overwritten; the loud line and `sync_revert_of`
make it visible after the fact. Acknowledged in the code: indistinguishable
in principle, and the reverse mistake is the one that actually cost
something. This is an L28 amendment (human-wins gains a sync-revert
carve-out) and is folded into Ledger §1 at the 09-09 addendum.

### Deviation, and it is a real bug found on the way
`ensure_schema()` globs `migrations/*.sql`, so **it would have run the
rollback script on every boot**, right next to the forward one. As it
happens `.rollback.sql` sorts *before* `.sql`, so today it would have
dropped the column and re-added it — harmless by luck, and exactly the
luck that stops holding at the next migration. `forward_migrations()`
now filters, with a test.

## E. The sheet probe reads the banner

**Commit** `9da3529`.

### The thirteen-hour green
The ASET sheet answered HTTP 200 from roughly 19:00 on 09-08 until 07:06
on 09-09 while the page carried *"⚠ DAY MODE UNRESOLVED — cards are
refused until this is fixed"*. `sheet_http` was green throughout and was
telling the truth: the server was up. It was answering the wrong
question.

The cause is the shape being watched for: the 09-08 seat-usage deploy
added a `TunableUnit.WINDOW` row to `tunables.yaml`; the sheet re-reads
that file per request through code that predated the enum value, so every
render raised `TaxonomyConfigError` — and `_daymode_state()` catches
everything and paints a banner, *deliberately*, because a sheet that will
not paint is a sheet he cannot trade beside. **A page that refuses cards
politely is externally indistinguishable from one that works.**

### What changed
`GET /api/health` on the sheet returns `{ok, day, mode, stage,
sheet_mode, error}` **from the same `_daymode_state()` call the page
renders from** — one resolver, two renderings, so the endpoint cannot say
green while the page shows the refusal. No data write (only the
idempotent `ensure_schema()` the render already makes), no LLM, and it
never raises: a config failure is the thing it exists to report.

`ok` is false iff `error` is set **or** `mode` is null — to a trader
those are the same thing, since `assert_sheet_matches` refuses every card
either way.

New probe `sheet_daymode`, in the beat immediately after `sheet_http`,
which is unchanged. Unreachable or an unrecognised payload is
**UNKNOWN, which is red**; a refusal is red and *not* unknown — the sheet
said what was wrong and the probe read it, truncated to 160 chars.

## ESCALATE

1. **F19's literal guard has been INACTIVE in every git worktree, and
   silently.** `cobalt.redact.secrets` resolved `data/.cobalt_vault`
   relative to the checkout; no worktree has a `data/`, so
   `load_literals()` returned "vault file … does not exist — literal
   guard INACTIVE" and nothing was red, because a locked vault is a
   legitimate state on most processes. Every Code prompt since the
   worktree rule (R4, 09-08) has run with the literal half of the
   exfiltration guard off. Fixed here with a fail-loud
   `COBALT_VAULT_FILE` override, but **the class of bug is the finding**:
   a guard whose "off" state is indistinguishable from a normal one.
   Worth deciding whether a worktree run should be *refused* rather than
   degraded.

2. **I leaked a credential into this session's transcript.** Adding the
   worktree `.env` line, I ran `tail -6 .env` to confirm the write, and
   the output carried `MATTERMOST_DB_PASSWORD=<value>` in cleartext. The
   value is now in this session's history. **Recommendation: rotate the
   Mattermost DB password** (`ops/mattermost_role_provision.py` is
   add-only and will refuse — a rotation path has to be written, which is
   itself an owed item). No other secret was printed; every later command
   used `-e VAR` by name or piped through `sed`. My failure, reported in
   full.

3. **The `.env` bootstrap tier is growing and has no rotation path.**
   Four credentials now live there (`POSTGRES_*`, `MATTERMOST_DB_*`,
   `COBALT_DB_*`, plus the master key). Both provisioning scripts are
   *mint-only* and refuse an existing key by design. Item 2 makes the
   missing rotation path concrete rather than theoretical.

4. **`reads` covers RE-READS, not read-once.** `com.cobalt.agent` (old
   tree) caches its settings in a singleton at first construction
   (`cobalt_agent/config.py:410`), so it truthfully declares `reads: []`
   and still must be restarted when `configs/*.yaml` changes. Until that
   second field exists, `cobalt jobs readers` answers "nothing to
   restart" for a file the old agent is running stale values from. It
   wants a `reads_at_start:` field; I did not add one because the prompt
   scoped this to re-reads and a guessed second list is worse than none.

5. **`ops/README.md` may conflict with `ops/mainframe-p5`.** I did not
   touch `ops/start_mainframe.sh` or `ops/mainframe/`, but item H
   rewrites `ops/README.md` including the mainframe row and the 09-03
   paragraph. Check at merge time.

6. **The sync-revert window has an unfalsifiable edge.** A human who
   hand-types a byte-identical copy of one of the last ten blocks Cobalt
   wrote into that unit is treated as a sync. Indistinguishable in
   principle — the bytes are the only evidence — and the reverse mistake
   is the one that cost an hour and forty minutes. Named in the code;
   flagging it so the ruling is his and not mine.

7. **`restore` still refuses a unit row whose write created the
   section.** The early guard (`before` is NULL → "restoring would mean
   deleting a section") fires before the per-unit path, so the finest
