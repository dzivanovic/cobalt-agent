## CAUSE
(d2) runs `validate`, which reads production `trader_settings` and needs the APP credential. It passed on 10-03 and 10-04 only because their hub ran it inside the dev-DB lock, where a copy of the production `.env` sits in the gate (steps 1b and 2b). `d483a417`, shipped by set 3b, moved it outside the lock (steps 2c to 2e). Proof: steps 1b, 2b, 2e and 3b. The code and dependencies are unchanged (step 4c).

## FIX
- Smallest correct fix: a card plus a hub line. The card gives `cobalt validate` a no-DB mode, for example `--no-db`. In `src/cobalt/cli.py` `validate`, that mode skips the `load_sheet_modes_config()` block and every check that depends on it, and prints that it skipped them. The card is (`cli.py:168-` the sheets/day-mode/band checks).
- Then `DEPLOY-HUB.md:101` (d2) runs `COBALT_ENV=production uv run cobalt validate --no-db`. The skipped DB checks are covered by the post-merge `validate` the hub already runs (`:74`, D2.4), from `/Users/cobalt/cobalt` with its own `.env`.
- Wrong: restoring "first thing inside the lock" (it would need `gate.sh` to run validate in its lock window), or putting any `.env` in the gate for (d2). Either one points the gate at the production DB with production credentials (L41, L76).
- Note: that is what the old order already did. Set 2d and set 3b ran a `COBALT_ENV=production` read against `cobalt_brain` from the gate on the copied production `.env`.
