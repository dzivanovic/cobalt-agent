## §2 Steps

- **STEP-1 (hub, before Sol; prod reads only):** cut the fixtures, see §3.
- **STEP-2 read layer:** add `RadarStore.members_for_day(pool_key, trade_date) -> list[dict]` (open + left, every F2 column) in `src/cobalt/radar/store.py`. It is the one store for these tables (L3). The pool block comes from `TraderSettingsStore.values()["radar.pool"]`. The session comes from `session_clock().session(now_utc())`. The interval comes from `load_tunables()` `radar.scan_interval`.
  - **[amended 09-15 per Astra R1-1]** `members_for_day` returns every episode row for the day, but the builder must distinguish **admitted** episodes (`entered_at IS NOT NULL`) from **never-admitted** exclusions (`entered_at IS NULL`, `store.py:84,89,95,113`): a promotion (`runner.py:273`) closes a never-admitted episode without it ever entering. `radar_pool.members` compares only against currently-open admitted rows (`entered_at IS NOT NULL AND left_at IS NULL`). Departed admitted episodes render separately from never-admitted exclusions; entry/exit churn counts admitted transitions only.
  - **[amended 09-15 per Astra R1-2]** `session_clock().session(now_utc())` can return `MARKET_RESET` or `OVERNIGHT`, values `RankMetric` has no key for (`session/models.py:22` five values vs `radar/models.py:87` three fields). The builder must not index the metric name by the raw clock session — resolve current clock state separately from the stored scan's own session/metric label (which ranks were computed under), and render without raising during reset/overnight. The plan's STEP-D2 "first post-reset scan lands ~21:00" (§6) is wrong: the runner is idle overnight: STEP-D2 smoke proves restart/idle only; live-scan acceptance waits for the next scanning session.
  - **[amended 09-15 per Astra R2-2]** `members_for_day`'s trading day is derived from the pool row's own last-scan timestamp converted to ET (`radar/pool.py:205` uses `now.astimezone(ET).date()`), never from wall-clock "today" at request time: at midnight the resident is idle (`runner.py:161-164`, session not in `SCANNED`) and the pool still describes yesterday, so a request for "today" against yesterday's nonzero `members` must not render an empty current pool. Rollover (`radar/pool.py:205-213`) closes prior-day open episodes with a backdated 20:00 ET `left_at` on the *next* scanning cycle, not at midnight — the panel labels retained prior-day data with its actual date and a staleness note rather than presenting it as current.
  - **[amended 09-15 per Astra R1-6]** `TraderSettingsStore.values()["radar.pool"]` can raise (key absent) or return a malformed/null block before any view exists (`settings/store.py:54`); validate it through the existing `PoolBlock` model (`radar/models.py`) after checking mirror `status`/`error` (F4 amendment below). Any of: missing pool row, non-`ok` status, missing/malformed block, absent scan timestamp, or a store read exception → FAILED per L1 (no plausible-empty artifact) — never a caught exception rendering zero rows.
- **STEP-3 view models + builder:** new `src/cobalt/aset/radar_panel.py`.
  - `PoolView` / `PoolRow` / `ChurnDelta`: rows ordered by `last_rank`, left rows with `left_at` + `excluded_by`, churn = `entered_at > since` / `left_at > since`. `since` is the client's last server timestamp, so the server keeps no state.
  - **[amended 09-15 per Astra R1-7, refined R2-1]** `since` is untrusted client input: reject absent/invalid/future values explicitly (never silently default); membership timestamps are assigned at scan start, before commit (`runner.py:162,183`), so advancing the client's watermark to the HTTP response time can permanently miss a transition committed after the response but stamped earlier. The server returns a watermark tied to what it actually observed as committed, not wall-clock-at-response; the client never advances its cursor on a failed refresh. The initial `GET /radar` HTML render has no prior cursor: it is an explicit snapshot (no churn labels, since there is no "previous" to compare against) that embeds its own observed watermark into the page for the first background `fetch` to use. `since` on `GET /api/radar/pool` must be tz-aware (`session/clock.py:262`'s `to_et` already refuses naive datetimes — reuse that posture): missing/malformed/naive/future values are rejected, not defaulted.
  - Fail-loud (L1/L9): missing pool row → FAILED; `degraded` → red banner naming `degraded_sources`; `failed_stage` → FAILED with detail; `last_scan_at` older than 2 × scan_interval → STALE banner; pool-block `status != ok` → FAILED.
  - `CardView` per card-spec §6 (dots, health, trails, etc.) + `LadderView`. Order: ARMED/TRIGGERED/IN-TRADE pinned above WATCH regardless of score; WATCH by `card_score` desc; terminal muted below.
  - **[amended 09-15 per Astra R1-4]** card-spec §6 alone under-specifies the fields R1's ladder needs: it carries no `card_score`, conviction, proximity, general lifecycle state or an owner field for manual stops (`card-spec.md:109,91` vs `cards/models.py:35`, `cards/store.py:196`). `CardView` adds these as typed presentation fields; unavailable ones are marked contract-only in the fixture (§3). The stored lifecycle value is `FILLED`; the display label is `IN-TRADE` — map, don't rename in storage. P3 displays the supplied contract values only; it does not implement card-spec §5 scoring/sizing computations (day budget/grade%/shares/risk-used stay untouched — that's a P2/write-path concern).
  - **[amended 09-15 per Astra R2-3]** R3's detail-column level 1 (trigger · stop · 1R · 2R) is not itself a sizing computation: `aset_sizings` already stores `entry` (the trigger) and `stop` (`cards/store.py:196`), and card-spec §5 defines 1R/2R as pure arithmetic on those two values (`distance = |trigger−stop|`; `1R/2R = trigger ± distance / 2·distance`, sign by `direction`). `CardView` computes and displays `target_1r`/`target_2r` from the stored `entry`/`stop` only — no grade%, day-budget or shares math, which stays out of scope. For the contract fixture (no real radar-origin rows yet), `target_1r`/`target_2r` are supplied fields, not derived, same as the other contract-only fields.
  - Card source adapter: open radar-origin rows in `aset_sizings`. 0 → empty state ("No radar cards — F8 lands in S2-P2"). >0 → FAILED ("radar cards exist but the card contract is not wired — S2-P2"), never a half render.

- **STEP-5 routes** in `web.py`: `GET /radar` (HTML, both layers, pool first) and `GET /api/radar/pool?since=` (JSON from the same builder, one path). A link to it from the sheet header. No POST route added.
  - **[amended 09-15 per Astra R1-3]** GET-only routes are necessary but not sufficient for "no write path": existing sheet render helpers (`_render` `web.py:368`, `_daymode_state` `web.py:476`, `_open_cards_section` `web.py:498`, `web.py:717`) can call schema init or persist a note attestation as a side effect of rendering. The new `/radar*` handlers call `RadarStore`/builder read methods directly and never reuse those helpers.   - **Focus fix (09-02 fumble):** the panel never calls `alert(`, `prompt(`, `confirm(`, `.focus(` or `autofocus`, has no inputs, and no `http-equiv="refresh"`. The refresh is a background `fetch` every scan_interval that swaps table content only.
  - **[amended 09-15 per Astra R1-5]** "Swaps table content only" must also refresh status/session/count labels and timestamps that sit outside the table, or they go stale silently. On a failed fetch (network/HTTP/JSON error) the panel shows a red refresh-failure banner and marks retained data stale — per L9, "a dead/changed source = red banner + degraded-mode flag, never silent staleness." A recovered refresh clears only the errors it actually fixed. Ladder expansion state (open/collapsed strips) survives a refresh.
