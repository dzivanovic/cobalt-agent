## 4. V3-2 — archive progress (desk resolution, §16 row V3-2)
- `BarStore.watermark()` stays for the poller and for reporting. It is NOT the archiver's progress: the poller advances `max(ts)` past bars that appear later (the desk's refuted V2-2 claim, `cto-2026-09-19.md` §13).
- **`archived_through` = the `ts` (bar OPEN, UTC) of the newest COMPLETE bar of an ACCEPTED export — a BAR timestamp, never a clock time, never a bar-close time, never `fetch_started_at`.** Monotonic across accepted runs (`GREATEST`); it never moves on a failed, withheld, empty or regressed target and never past that export's newest eligible bar. It records that the available export was processed through that key — not that the vendor supplied every bar.
- **ONE transaction on ONE connection per target** holds: the stored-range read, the inserts, the progress write, the incident writes and the accepted outcome. The store's append method and the progress/incident writers TAKE that connection. A crash between any two statements commits none of them. A failed or withheld target's transaction is rolled back; its failure evidence (the incident) is then persisted in a SECOND small transaction (Astra, V3-2: "Persist failure evidence separately after rollback").
- **Candidate range** of a target = every eligible bar (V2-3) of the download that lies in the UNION of (a) `ts > archived_through` and (b) the two most recent COMPLETED trading sessions at fetch start plus the current day — sessions being America/New_York calendar DATES that carry bars in the export (no 24-hour arithmetic; a weekend or holiday simply has no date in the export; DST-aware).
- **No progress row → BOOTSTRAP**: every eligible key of the available export is reconciled once (compare + DO NOTHING), regardless of rows the poller already stored; the report says `bootstrap`, states the bounds, and states that history before those bounds is UNASSESSED. An export with no eligible complete bar does not establish progress; the next non-empty night still bootstraps.
- A progress row is NEVER deleted — not when a ticker leaves the trader's list. A returning target meets its old `archived_through`, which is what makes the dropped-and-re-added sequence open a `gap` incident (round-2 sequence #8, SURVIVES).


## 9. Failure semantics and the lock (V2-9; stands)
One transaction per target (§4). The run continues after a failed target. A Postgres session-level advisory lock, ONE constant key, taken at the start of `run_full`, `run_backfill`, `restate --apply` and `backfill-missing`, in BOTH write modes; a second holder refuses loudly (`another archive/repair run holds the lock — <what it is, if known>`), exit code 2. The poller does not take it (R8). Run identity: `system.cobalt_jobs` has one row per label and no run id (§2), so `run_id` = `<label or command>@<run started_at, UTC ISO>` — a TEXT the report and the progress row share; no new run table.

## 11. The two additive tables and the promotion path
Both SYSTEM side (L32: market-data bookkeeping, nothing of one trader's choice; `placement.py` gains both; `cobalt_user` is granted nothing on them). Logical keys only — nothing about how `bars` is physically laid out (V2-8).
- **`system.archive_progress`** — `ticker TEXT`, `interval TEXT`, `archived_through TIMESTAMPTZ NOT NULL`, `export_oldest TIMESTAMPTZ NOT NULL`, `export_newest TIMESTAMPTZ NOT NULL` (eligible-bar bounds of the last ACCEPTED export), `raw_export_newest TIMESTAMPTZ` (diagnostic), `fetch_started_at TIMESTAMPTZ NOT NULL`, `bootstrap_at TIMESTAMPTZ NOT NULL`, `run_id TEXT NOT NULL`, `updated_at TIMESTAMPTZ NOT NULL`; `PRIMARY KEY (ticker, interval)`; `CHECK (archived_through <= export_newest)`. Written ONLY by the archiver in `append` mode, only in an accepted target's transaction, `archived_through = GREATEST(old, new)`.
- **`system.archive_incidents`** — `id BIGSERIAL PRIMARY KEY`, `kind TEXT CHECK (kind IN ('gap','restated','stored_only','empty_export','regression'))`, `ticker`, `interval`, `range_start`, `range_end`, `first_seen_at`, `last_seen_at`, `detail JSONB`, `resolved_at`, `resolved_by`, `run_id`; ONE unresolved row per `(kind, ticker, interval, range_start)` (partial unique index `WHERE resolved_at IS NULL`) — a recurring night refreshes `last_seen_at`, never duplicates. `regression` is added to v2's four kinds because V3-5 gives regression its own incident. `cobalt archiver incidents` lists the unresolved ones; the heartbeat's archiver probe (`heartbeat/probes.py:261`) is not green while any is unresolved. Resolution is explicit (`incidents resolve <id> --by <who> --note …`), audited on the row.
- **Migrations**: database-wide, `src/cobalt/db_migrations/`, numbers **`0010_archive_progress.sql`** and **`0011_archive_incidents.sql`**, each with its `.rollback.sql` (a plain `DROP TABLE` of its own table — additive, no other object touched), registered in `FORWARD` / `REVERSE` in numeric order. `0008`/`0009` belong to the unmerged `sprint-2/p4` and are NEVER used here; a gap in the tuple is legal (the registry is an explicit list, `__init__.py:40-58`; no test asserts contiguity). The branch that lands second rebases and keeps BOTH sets in numeric order. Ownership and grants follow `0006_radar_score.sql`'s pattern for a system table — the builder reads it, never invents one.
- **Promotion (L7's shape — it IS a flip from one source of truth to another):** deploy as `upsert` with the shadow on → **N shadow nights, N = PROPOSED 5 trading nights** (one full week, so a Friday→Monday boundary and the weekly vendor window roll are inside the sample) **— N is the OWNER's** → `shadow-report` numbers to him and to the tribunal record: would-withhold targets per night, field distribution, persisted/vanished/appeared, late/new counts, measured cost of the steady-state read → **his explicit ruling to switch**, which must also accept or refuse the KNOWN LIMIT of §12 in words (Astra: "Tribunal agreement counts do not settle it"). No percentage, no threshold, no automatic switch. The first `append` night is the BOOTSTRAP night: about one old-style night of key reads, no row rewritten.
